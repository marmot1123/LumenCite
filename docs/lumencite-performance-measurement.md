# LumenCite パフォーマンス計測：実装担当LLMへの指示

## 1. 依頼と到達点

LumenCiteを使った文献検索・読解で「回答まで1分以上待つことがある」という体感を出発点に、現状の性能を計測してください。最初の目的は高速化の実装ではなく、**どの質問で、どの区間に、どれだけ時間がかかり、利用者が何を待っているか**を再現可能な形で示すことです。

この文書は会話から作った計測計画であり、現在のリポジトリを調査した結果ではありません。以下の処理名・ログ項目・配置例は提案です。既存実装を確認して対応づけ、未実装の機能を存在するものとして扱わないでください。

まず既存の計測機能を利用し、不足箇所に最小限の計装を加えてベースラインを取得してください。新しい検索方式、埋め込みモデル、複合MCPツール、キャッシュ、URI体系の導入は、この依頼の完了条件ではありません。計測前に最適化して元の状態を失わないでください。

最終的に、次の問いへ回答してください。

1. LumenCite内部の検索・LCIR取得自体が遅いのか。
2. MCP経由の転送・呼出し回数・出力量が待ち時間に関係しているか。
3. 外部LLMクライアント内の処理・待機が大きいのか。どこまで観測できたか。
4. 起動直後、キャッシュ状態、文献規模、質問の種類でどう変わるか。
5. 正しい根拠が初めて使えるまでの時間と、最終回答までの時間はどう違うか。

## 2. 背景と評価対象

LumenCiteは、研究者が手元に持つ文献をLCIRの構造に基づいて参照し、LLMへ根拠を渡す用途を想定しています。速度だけでなく、定理の仮定・結論・文献の版を保って原典へ戻れることを評価してください。

質問を次の3種類に分けます。これは評価上の分類であり、3本の実装経路や自動振分けが既にあるという意味ではありません。

| 分類 | 例 | 成功したときに利用者が得るもの |
| --- | --- | --- |
| A：既知項目の取得 | 指定文献の定義2.1、定理2.3、式(4.7)を示す | 指定した版の正しい本文・式と原典参照 |
| B：ファジーな想起 | 「このような仮定で弱収束を示した論文があったはず」を探す | 妥当な候補と、その判断を確認できる正確な主張 |
| C：複数文献の統合 | 複数の定理の仮定を比較する／related workをまとめる | 複数の原典へ接地した説明・比較・草稿 |

「ローカルなら数十ミリ秒」「意味検索＋一回の再順位付けなら10秒」といった会話中の見立ては未検証の仮説です。ボトルネックや採用すべき方式を先に決めないでください。

## 3. 最初に実装と環境を確認する

リポジトリの作業指示を読み、作業中の変更を保持して、以下を短く記録してください。

- コミットID、未コミット変更の有無、LumenCite・LCIRスキーマ・抽出器の版。
- OS、CPU、メモリ、ストレージ、電源状態、ビルド種別。実利用に近いreleaseビルドを基準にし、debugとは別集計にする。
- 実際の利用経路：UI、MCPクライアント、MCPトランスポート、起動・接続方法。
- 文献登録、抽出、索引作成、検索、LCIR読込、応答生成の実際の呼出し関係。
- 既存のベンチマーク、ログ、トレース、機能フラグ、キャッシュ、タイムアウト。
- 外部クライアント名・版、選択モデル、表示される推論設定、会話状態、公開ツール数。取得できない情報は「不明」とする。

最初のベースラインは索引・LCIR構築済みの読取経路とします。初回取込・再構築は別の作業負荷として扱います。ただし検索中に暗黙の再構築が起きる場合は除外せず、その事実と所要時間を記録してください。

## 4. 計測を3層に分ける

| 層 | 実行方法 | 主に分かること |
| --- | --- | --- |
| L1：内部処理 | 既存のサービス／検索関数等を固定入力で呼ぶ | DB検索、LCIR読込、整形などのローカル処理時間 |
| L2：MCP往復 | LLMを使わない小さなクライアントから実際のMCP経路を呼ぶ | 固定要求に対する往復時間、サーバー処理、転送量 |
| L3：実利用 | 普段のLLMクライアントで固定プロンプトを送る | 質問から根拠表示・最終回答までの体感と実際のツール列 |

L1が直接呼べない場合は無理に大改造せず、L2のサーバー内計装で補い、その制約を書いてください。L2の固定要求はL3で実際に使われた要求を参考にし、入力と結果量を揃えて比較します。直接取得できないB・CをL1だけで「完了した質問」と数えないでください。

MCPの初期接続・ツール一覧取得を含む試験と、接続済みセッションの試験を区別してください。固定ツール列の再生は処理コストの比較であり、LLMの探索判断を含む実利用の代替ではありません。

## 5. 時間指標の定義

経過時間は同一プロセスの単調増加時計で測定し、壁時計の日時は実行の識別・概略の対応づけに使います。異なるプロセスの単調時計をそのまま引き算しないでください。

L3では、質問送信操作の確定を `t0` とし、以下のイベントを記録してください。

| 指標 | 終点・定義 |
| --- | --- |
| `first_progress_ms` | 最初の進捗表示まで。「検索中」等で、根拠とは区別する |
| `first_candidate_ms` | 最初の候補文献・ノードが利用者に見えるまで |
| `first_evidence_ms` | 質問に関連する本文・式等と出典が、確認可能な形で初めて見えるまで |
| `final_answer_ms` | クライアントが最終回答を完了したと判断できるまで |
| `first_tool_start_ms` | 最初のツール呼出し開始まで。観測可能な場合のみ |
| `tool_call_count` | その質問中の全ツール呼出し数。失敗・再試行も含む |

すべての時間指標は起点と終点を明示してください。最初のトークンや「8件発見」を最初の根拠と数えないでください。誤った候補本文は有用な根拠に数えず、初回候補と正しい根拠への到達を分けます。根拠を表示するUIがなければ、最終回答中で初めて確認できる時点を使います。表示時刻が取れない場合はnullとし、ツールが根拠を返した時刻を別指標で報告してください。

L2ではクライアント送信から応答受信完了までを測り、L1／サーバー内では実際に存在する以下の区間を測ります。

- 要求受付後の待機、ハンドラ開始、入力処理。
- 文献・版・ノード識別子の解決。
- 検索、候補の絞込み、再順位付け（存在するもののみ）。
- DB問合せ、ファイルI/O、LCIR読込・解析・構築。
- 根拠の組立て、応答シリアライズ、応答サイズ。
- キャッシュのヒット／ミス、ロック・キュー待ち（観測できる範囲）。

親spanと子spanは包含関係を保持し、重複を含んだまま合計しないでください。並列処理では総作業時間と経過時間を分け、可能ならクリティカルパスを示します。

L3でツールの開始・終了がすべて同一時間軸に取れる場合、区間の和集合から「ツール待ちを含む区間の長さ」を出せます。それを全体から差し引いた値は**クライアント側等の未分類時間**であり、LLM推論時間と断定しないでください。通信、待ち行列、UI描画なども含み得ます。観測不能なら推定値を作らないでください。

## 6. 最小限のログ

計測を設定でON/OFFできるようにし、既存のログ／トレース基盤を優先してください。MCPがstdioなら、ログをプロトコル用stdoutへ混ぜず、stderrまたは専用ファイルへ出します。

最低限、次の情報を機械可読なJSONL等に保存してください。名称は既存規約に合わせて構いません。

```text
run_id, scenario_id, layer, cache_condition, session_condition
trace_id, span_id, parent_span_id, process_id
event_or_operation, start_offset_ms, duration_ms
status, error_type, timeout_ms, retry_index
tool_name, request_bytes, response_bytes, result_count
cache_name, cache_hit, db_query_count, lcir_load_count
observation_method, unavailable_reason
```

取得できない値はnullとし、0で埋めないでください。トークン数は取得可能なら記録し、概算なら推定方法も記録します。バイト数をトークン数と同一視しないでください。

サーバーspanとMCP要求IDを対応づけ、L3の一質問に複数呼出しがある場合も追跡できるようにします。外部クライアントでIDを伝播できない場合は、実行を分離し、時刻と呼出し順で対応づけたことを記録します。

本文全文・認証情報を通常の性能ログへ出さず、文献・版・ノードの識別子、サイズ、件数を基本としてください。再生に必要な固定入力や期待結果はベンチマーク用fixtureへ分けます。

## 7. 代表質問10件を固定する

実際に登録された文献から次の構成で選び、曖昧なプレースホルダーを具体的な質問に置き換えてください。試験前に原典で期待結果を確定します。初回は大量の人工データより実際の遅さを再現する文献を優先します。

| ID | 種類 | シナリオ | 正しさの確認 |
| --- | --- | --- | --- |
| A1 | 既知 | 文献と版を指定して定義を取得 | 定義本文と位置が一致 |
| A2 | 既知 | 指定した定理を仮定込みで取得 | 側条件・結論が欠けない |
| A3 | 既知 | 式番号で数式と周辺文脈を取得 | 数式、番号、版が一致 |
| B1 | 想起 | 内容の言い換えから定理を探す | 正解ノードが候補に入り、到達できる |
| B2 | 想起 | 日本語の記憶から英語文献を探す | 妥当な候補と主張に戻れる |
| B3 | 想起 | 似た主張や別版が複数ある状況で探す | 仮定・版の違いを区別できる |
| B4 | 想起 | 登録文献内に正解がない質問 | 不在または未発見を適切に示す |
| C1 | 統合 | 2文献の定理の仮定を比較 | 各比較項目に対応する根拠がある |
| C2 | 統合 | 固定した3〜5文献からrelated workを作る | 主要主張の出典が確認できる |
| C3 | 統合 | 指定コーパス内の研究の流れを整理 | 対象範囲・版・根拠を明示する |

シナリオごとに、プロンプト、対象文献・版のID、正解ノードの集合、許容する別解、成功条件、タイムアウト、必要な事前状態を保存します。ノードIDがなければ原典ハッシュ＋ページ／節等で代用し、URIの新設を前提にしません。

B1〜B3は、候補一覧が観測できる場合にHit@kや正解順位も記録してください。B4の未発見は、この固定コーパス内の評価であり、分野全体に論文が存在しないという断言を正解にしないでください。

Cは文章の完全一致を要求せず、重要な主張と根拠の対応、仮定の欠落、版の混同、根拠のない断言を確認します。LLMによる採点のみを正解判定にせず、固定した確認項目と原典を使ってください。

## 8. 実行手順と反復数

### 第1段階：低負担で原因を絞る

1. 実ライブラリまたは安全な複製を固定し、文献数、LCIRノード数、DB／LCIRの容量、原典の種類を記録する。
2. L3で代表質問10件を各1回実行し、実際のツール列、時間、成功／失敗を残す。これは動作確認と遅延の探索であり、P95を評価するデータ量とは扱わない。
3. A・B・Cから代表各1件を選び、各3〜5回追加して揺らぎを確認する。遅いケースが別にあれば対象へ加える。
4. 観測した主要ツール要求をL2で固定入力として再生し、必要箇所にL1またはサーバー内計装を加える。
5. 全質問の結果と、遅い代表実行の内訳を報告する。ここまでで有用なベースラインを完成させる。

### 第2段階：ローカル経路を安定して比較する

- L1／L2の主要ケースは、ウォームアップ5回を別記録にしてから、同一条件で30回を初期目安として測定する。
- 詳しく調べるケースだけ100回以上へ増やし、末尾遅延の傾向を確認する。100回でもP95が十分安定する保証はない。
- プロセス再起動後の初回アクセスを5回程度測り、各回の値を示す。
- L3は高コストで変動もあるため、初回から全件100回などを要求しない。小標本では個別値、中央値、最小・最大を中心に報告する。
- 単一利用者・同時要求1を標準とする。実利用で並列要求が確認された場合、その観測した並列度を追加する。無関係な負荷試験を先に広げない。

反復数は予算と実行時間に応じて調整し、変更理由と実数を残してください。ユーザーの操作が必要なL3を実行できない場合は、L1／L2を先に終え、送るプロンプト、操作順、記録表を用意してください。実施していない試験を実測済みと報告しないでください。

### キャッシュと会話状態の扱い

| 条件 | 定義 |
| --- | --- |
| process-cold | プロセス再起動後の初回。OSのページキャッシュが残っていてもよいが明記する |
| app-cache-cold | テスト用環境でアプリの該当キャッシュだけを安全に空にした状態 |
| warm | 事前実行済みで、キャッシュが有効な通常状態 |

OSキャッシュまで消した「完全cold」を安易に主張しないでください。ユーザーの原典・DB・索引を削除してcoldを作らず、再生成が必要な試験は複製・fixtureで行います。

L3は新規会話を原則とし、同じ質問が会話履歴から回答されないようにします。継続会話を試す場合は別条件にします。新規会話でもサーバー側キャッシュは残り得るので、会話状態とキャッシュ状態を別々に記録してください。

## 9. 集計と品質

- シナリオ×層×キャッシュ条件×クライアント／モデル条件ごとに集計する。A・B・Cを混ぜた一つのP95だけで結論を出さない。
- 試行数、成功数、失敗数、タイムアウト数、中央値、最小・最大、必要に応じてP95を示す。
- P95を出す場合は計算法を固定する。例：昇順のn件の `ceil(0.95*n)` 番目を採用。少数試行では参考値と明記する。
- 成功した試行の時間だけを出す場合は、その条件付き統計であることと全試行の成功率を併記する。
- タイムアウトを完了時間として混ぜない。打切り時間と未完了を保存し、失敗を黙って除外しない。
- 再試行した場合、利用者が待った時間には再試行・待機も含める。個々の試行も別途残す。
- 外れ値は残し、既知の外乱がある場合に限って理由付きの補助集計を追加する。

固定したケースで計装ON/OFFを比較し、計装自体の影響が無視できるか確認します。同期的な大量ログ等で測定対象を遅くしている場合は修正し、その経緯を記録してください。

画面録画・手動計時を使った場合は、測定方法とおおよその分解能を記録します。秒単位の観測をミリ秒精度の実測として扱わないでください。

## 10. 会話中の時間目標の扱い

以下は将来のUX目標の候補です。達成済みの性能や、この計測作業の合否条件ではありません。

| 対象 | 暫定的に観察する目標 |
| --- | --- |
| 最初の有用な根拠 | 質問送信から3秒以内 |
| A：単純な取得 | LLM経由でも最終結果10〜15秒以内を目指せるか |
| B：ファジー想起 | 正しい候補・主張への到達が10秒級になるか |
| C：統合 | 最終完成時間に加え、根拠が途中から利用可能になるか |

各閾値以内の成功数／全試行数も示せると有用です。Cの最終時間は文献数や依頼量に依存するため、まず条件を固定して実測します。L1／L2の処理時間とL3のUX目標を直接比較しないでください。

## 11. 結果から次の一手を選ぶ

改善案は実測の根拠と結びつけ、最大3件に絞って優先順位を付けてください。以下は診断の候補であり、決めつけではありません。

| 観測 | 次に検証する仮説 |
| --- | --- |
| DB問合せ／LCIR読込が候補件数に比例して増える | N+1や重複読込があるか |
| LCIR解析・組立てが要求ごとに長い | 同一データの再構築が支配的か |
| L1は短いがL2が長い | 応答量、直列化、接続・転送・待機の影響か |
| L2は短いがL3が長い | ツール往復数やクライアント内の未分類時間が大きいか |
| Bだけ探索回数が多い／正解候補が出ない | 現在の検索とクエリ変換のどこで取り逃しているか |
| 最終回答は遅いが根拠自体は早く取得済み | 根拠を表示するまでの待ちが大きいか |

「ツールが多いから遅い」「返却量が大きいから遅い」は、件数・サイズの観測だけでは因果を確認したことになりません。比較する場合は入力と品質条件を揃え、一度に変える条件を絞ってください。キャッシュ等の改善余地も、対象区間の占める時間を超えて全体が速くなると見積もらないでください。

## 12. 成果物と完了条件

既存のリポジトリ構成に合わせ、次を残してください。以下の名前は配置例です。

```text
benchmarks/performance/README.md       # 前提・起動・再実行・集計の正確な手順
benchmarks/performance/scenarios.json # 固定プロンプト・期待結果・条件
benchmarks/performance/               # 必要最小限の実行・集計スクリプト
performance-results/<run-id>/
  environment.json                   # 環境・版・コーパス情報
  events.jsonl                       # 生ログ
  summary.csv                        # 集計結果
  report.md                          # 診断と次の判断
```

私有コーパスや本文をGitへ追加しないでください。公開用fixtureと手元の実データの測定結果は区別します。

報告書には、代表質問10件の結果表、L1／L2／L3の違い、遅いケースの時間内訳、正しさの判定、未観測区間、再実行方法、次の改善候補を含めます。内部spanを合計しただけの内訳ではなく、包含・並列関係が分かる説明にしてください。

完了条件は次のとおりです。

- [ ] 実装と計測点の対応が分かる。
- [ ] 固定した質問・コーパス・環境・状態で再実行できる。
- [ ] 生データと集計が残り、失敗や未測定を判別できる。
- [ ] ローカル処理と実利用全体の遅さを、観測可能な範囲で区別できる。
