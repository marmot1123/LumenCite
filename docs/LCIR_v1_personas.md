## この文書の位置づけ

v1.0.0 のリリースで LCIR（LumenCite Document Intermediate Representation）は一応の完成に達する。
本書は、その時点の LumenCite が研究者の日々の作業をどう変えるかを、5 人のペルソナの作業シナリオとして描く。
形式は、想定ユーザー像ごとに具体的な一日の流れを追うペルソナ分析に倣う。
リリースノートや紹介文の素材として、また「何のためにこれを作ったのか」を後から振り返る記録として使う。

前提が 2 つある。
第一に、本書が使う能力はすべて、2026-08-04 時点の実コードか、v1.0.0 スコープ（`docs/LCIR_REMAINING_PHASES.md` §0 の中間 9 項目）で確定した設計に裏づけを持つ。
執筆時点で中間 9 項目のうち抽出器側 5 項目は main にマージ済み（リリースと実 DB への反映は v1.0.0 の再構築とタグで行う）で、残る p1〜p4（FTS 派生化、自動 build、既定 ON と同意分離、superseded 版の GC）は未実装である。
本書は 9 項目すべてが出荷された「v1.0.0 リリース後」の世界を描く。
第二に、v1.0.0 の LCIR には意図的にやらないことがある。
各ストーリーの末尾と「v1.0.0 の LCIR がしないこと」の節に、その境界を明記する。

## v1.0.0 時点の LCIR の能力

**LCIR** は、論文全文を「ページ単位のプレーン文字列」ではなく、型付きノードの木、PDF 座標、出典（provenance）、信頼度の組として SQLite に保存する中間形式である。
研究者から見える能力は次の 4 群にまとまる。

- **構造の保存**：節、段落、caption、参考文献、display 数式、定理系 8 種（定理、補題、証明ほか）、図領域、表を型付きノードとして持つ。
  PDF からはレイアウト推定で（信頼度付き）、arXiv TeX ソースからは原文どおりに取る。
  ただし表のセル構造と記号定義は TeX 版に限る。
  数式は TeX 版なら原文の生 LaTeX、PDF 版なら表層文字列で保存される。
- **関係の保存**：`\ref` や `\cite`、本文中の番号照合から、cites、refers_to_equation、proves、caption_of などの型付き参照グラフを張る。
  TeX の定義文（"let $X$ be …" など）からは記号定義を抽出し、定義位置と出現に結びつける。
- **LLM への露出**：MCP サーバー（read 系 17 ツール）、アプリ内チャット、CLI が同じ実装を共有する。
  文献本文系は `get_fulltext` に加えて LCIR 8 ツール（`get_document_structure` / `get_document_blocks` / `search_document_nodes` / `get_node_relations` / `get_symbol_definitions` / `get_figures` / `get_tables` / `get_node_context`）。
  応答には origin と confidence が付き、原文由来と推定を区別できる。
  チャットでは結果カードから PDF の該当領域へ跳べる（PDF 由来の結果に限る）。
- **v1.0.0 で足される運用面**：新規添付で LCIR build が自動で走り（p2）、`lcir.enabled` は既定 ON になる（p3。外部通信を伴う TeX 自動取得は別の同意フラグに分離）。
  全文検索の索引源は LCIR 優先になり（p1）、superseded 版の GC と容量可視化が付く（p4）。

## ペルソナ 1: 長編プレプリントを査読するポスドク

数理物理のポスドク。
査読と共同研究の下調べで、月に数本の長い arXiv プレプリントを精読する。
この分野は論文ごとに記法が違うため、これまでは「$\mathcal{R}$ が最初に定義された場所」を PDF ビューアの文字列検索で探し回り、"by Lemma 4.2" と書かれるたびに 20 ページ前へ戻っていた。
LLM に PDF を丸ごと渡す手も試したが、返ってくる式が原文どおりかを毎回目視で確かめ直す必要があり、確認の手間が読解の速さを食い潰していた。

朝、査読対象の 60 ページのプレプリントを arXiv ID で追加する。
PDF が自動で添付され、v1.0.0 では添付と同時に LCIR build が走る。
TeX 自動取得にも同意してあるので e-print も取り込まれ、PDF 版と TeX 版の 2 つの抽出結果が併存する。
ターミナルの Claude Code には LumenCite を MCP 接続してあり、そのまま精読を始める。

「§3 の $\mathcal{R}$ の定義はどこか」と聞くと、Claude は `get_symbol_definitions` で定義文と定義位置、出現一覧を引く。
式 (3.12) の正確な形が要る場面では `get_document_blocks` を display_math に絞って呼ばせる。
TeX 版のブロックには原文の LaTeX がそのまま入っているため、答えに出てくる式をそのまま脳内コンパイルで検算できる。
主定理の依存関係は `get_node_relations` で確かめる。
TeX 版の辺は `\ref` と `\cite` の解決なので確信度が高く、「Theorem 5.1 の証明は Lemma 4.2 と式 (3.12) に依存する」という答えに根拠の辺が付く。
定理 5.1 を読む段では `get_node_context` に node_id を渡すと、TeX 版なので主張の全文に加えて、前提となる $\mathcal{R}$ の定義文と参照している式まで束ねて 1 回で返る（PDF 版のノードで呼んだ場合は、ページをまたいだ主張の続きを読み順で再結合する方が効く）。
査読レポートに書くページ番号は、TeX 版が座標を持たないので、`search_document_nodes` で該当フレーズを引いて PDF 版のヒットが返すページと領域を使う。
最後に CLI で構造付き Markdown を書き出し、手元に残して午前の精読を締めた。

定義の逆引きと依存確認が、PDF を前後に往復する手作業から数回のツール呼び出しに変わり、査読レポートに載せる引用にはページ番号つきの裏が取れる。

v1.0.0 でも、数式は TeX 版で生 LaTeX の文字列止まりであり、「この式とあの式は同値か」のような構造照合はできない（数式 AST は post-1.0）。
参照グラフは「誤検出より欠損」の方針で作られるため、解決できない参照や複数形の参照（"Figures 3 and 4"）は張られず、依存関係の網羅は保証されない。

## ペルソナ 2: 輪講で古典論文を担当する博士課程学生

偏微分方程式論の博士課程学生。
週次の輪講で、1990 年代の雑誌論文の担当が回ってきた。
出版社 PDF しかなく、arXiv ソースは無い。
定理番号と図の参照が入り組んだ論文で、これまでは印刷して付箋を貼り、レジュメに載せる引用のページ番号を手で拾っていた。
LLM に PDF を渡して質問しても、答えに「どのページの話か」が残らず、輪講で突っ込まれたときに根拠へ戻れないのが不安だった。

出版社の論文ページで Chrome 拡張のクリッパーを押すと、DOI が解決されてエントリと PDF 添付ができ、LCIR build も自動で走る。
図の説明が欲しいので、Vision alt text の同意フラグを有効にして生成バッチを一度だけ回しておく[^vision]。
アプリ内チャットでセッションのスコープをこの論文 1 本に絞り、「Theorem 2.3 の証明はどの補題と式に依存するか」と聞く。
チャットは `get_node_relations` を呼び、番号照合で張られた proves 辺と参照辺を、端点のページとスニペットつきで答える。
PDF 経路の辺は推定（confidence 0.6〜0.7。TeX 版の 0.9 より低い）だと結果に明示されるので、怪しい辺だけ自分で原文に当たればよい。
「Figure 3 は何を示しているか」には `get_figures` が caption と生成 alt text、ページと領域を返す。
回答カードのチップを押すと PDF ビューアの該当領域へ跳ぶ。
この論文の相図は描画命令だけのベクター図だったが、caption と対にできたベクター領域として拾われていた。
式 (2.9) は `get_document_blocks` で数式番号つきの表層文字列として引ける。
ただし PDF からは LaTeX が復元されないため、チップで現物を見て自分の手でレジュメの LaTeX に起こす。
根拠集めは `search_document_nodes` で行い、ヒットが返すページとスニペットをそのまま「p.7, 式 (2.9)」の形で引用に使う。
仕上げに、読解メモの下書きをチャットに書かせてノートへ保存させ、数式レンダリング付きのノートをレジュメの土台にした。

定理の依存関係と図の説明がページ位置に紐づくので、引用にページ位置の裏を付けた状態で輪講に臨め、質問されたらその場で該当箇所へ跳んで示せる。

TeX ソースの無い論文である以上、記号定義は引けず、表もセル構造化されない（どちらも TeX 専用で、PDF 側の表認識と記号抽出は post-1.0）。
PDF 経路の定理検出と参照解決は番号文字列の照合による推定であり、拾えない参照は欠損として残る。

[^vision]: alt text の生成は画像 1 枚ごとに外部 API 送信と課金が発生するため、LCIR 本体とは独立の同意フラグ（`lcir.vision_alt_text.enabled`）で opt-in する。
    生成文はヒント（origin=llm_inference）として返り、原文の caption を上書きしない。

## ペルソナ 3: レビュー論文を書く助教

数理物理の助教。
量子可積分系のレビュー論文を依頼された。
ライブラリには arXiv 論文が数百件あるが、Yang–Baxter 方程式や $R$ 行列の記法が論文ごとに違い、比較のたびに PDF を開き直して該当式を目視で探していた。
式を原稿に書き写すときは自分で LaTeX に起こし直すため、転記ミスが混ざる。
refs.bib はコピペの継ぎ足しで育てた結果、執筆のたびにキーの重複と欠落に突き当たっていた。

朝、原稿リポジトリを Claude Code で開き、lumencite-bib Skill を呼ぶ。
「ライブラリ内で Yang–Baxter 方程式を扱う論文を挙げて」と頼むと、`search_document_nodes` がライブラリ横断のブロック粒度検索で、各ヒットを書誌とページ、スニペットつきで返す。
比較対象に選んだ 3 本は arXiv TeX が取り込み済みなので、`get_document_blocks` から式番号つきの原文 LaTeX（$\check{R}_{12}(u-v)$ のような形のまま）が返り、$R_{12}(u)$ 系と $\check{R}$ 系の記法対応表を転記ミスなしで原稿に組める。
「この論文の $T(u)$ の定義は」と聞けば `get_symbol_definitions` が定義文と定義位置で答え、定義探しのために PDF を開かない。
主定理を引用する段では `get_node_context` に node_id を 1 つ渡すだけで、主張の全文、前提定義、参照辺が 1 回で揃い、言い換えではなく原文準拠の引用文が書ける。
本文に書いた `\cite` キーは `find_entries_by_citation_keys` で棚卸しし、`export_bibtex` で refs.bib を生成する。
応答の missing 配列が空になるまで、足りない文献を `search_entries` で探して埋める。
citation key はライブラリ全体で決定的なので、refs.bib を再生成しても原稿中の `\cite{baxter1972a}` は壊れない。
夕方、共著者への共有用に CLI で構造付き Markdown を書き出し、その形式で落ちる情報の警告を確認してから渡した。

PDF を開いて式を探す往復と手写しの LaTeX 起こしが消え、記法比較と定理引用と refs.bib 整備が同じセッションで完結する。

横断検索は表層の語彙一致であり、意味的に同じ式や言い換えを探す検索はできない（数式 AST と embedding は post-1.0）。
TeX が取れない出版社 PDF のみの文献では、数式は表層文字列に落ち、記号定義も表構造も付かない。

## ペルソナ 4: 蓄積を引用に変える准教授

数理物理の准教授。
10 年以上かけて数百本の arXiv 論文を溜めてきたが、実態は「PDF の山にメタデータが付いたもの」だった。
執筆中に「スペクトルギャップの一様下界をやっていた論文はどれだったか」となるたびに、タイトル検索と PDF の開閉を繰り返す。
定理番号や式の位置までは誰も覚えていないので再発見のコストが高く、過去の蓄積が引用に活きない。

朝、arXiv の new listing で気になった 3 本を Chrome のクリッパーで保存する。
エントリが作られ、PDF が自動で添付され、全文索引と LCIR build がバックグラウンドで走る。
TeX 自動取得も有効化してあるので、原文 LaTeX と定理ノードと記号定義を持つ TeX 版もできあがる。
取り込みに要る操作はクリック 1 回で、この時点では論文をまだ読んでいない。

3 週間後、原稿執筆中に Claude Code から頼む。
「スピン鎖のスペクトルギャップに一様下界を与えた定理を、以前保存した論文から探して引用まで付けて」。
Claude が `search_document_nodes` を "spectral gap lower bound" で呼ぶと、ライブラリ横断の検索が定理ノードのヒットを書誌とページつきで返す。
続けて `get_node_context` にその node_id を渡すと、ページをまたいだ主張の続きが読み順で再結合され、参照している式とともに束で返り、「探していたのは 2019 年の論文の Theorem 2.3、ただし周期境界条件が仮定」とまで特定できる。
$\Delta$ の流儀が怪しかったので `get_symbol_definitions` で定義文を確認する（TeX 版があるので原文由来である）。
引用は `resolve_citation_key` でキーを引き、`export_bibtex` で refs.bib に追記して `\cite` を挿す。

「保存して終わり」だった PDF の山が定理単位で検索できる資産に変わり、過去論文の再発見から `\cite` 挿入までがチャット 1 往復で終わる。

横断検索のヒットは PDF 版由来（TeX 版は重複ヒットを避けるため索引されない）なので、検索に当たる定理ノードはレイアウト推定であり、網羅は保証されない。
また、抽出器が改良されても既存文献の LCIR は自動では更新されず、設定画面の再構築ボタンを押すまで旧版のまま使われる[^rebuild]。

[^rebuild]: 自動再構築を意図的に結線していないのは、抽出器の版が上がるたびに全ユーザーへ無断で長時間の全再構築を走らせないためである。
    旧版の LCIR は設定画面の再構築ボタンでまとめて更新でき、実行時に対象件数が表示される。

## ペルソナ 5: 紙の蓄積を電子化するシニア教授

作用素環論の教授。
研究室の棚に、1970 年代からの紀要論文と絶版の lecture notes、自分の旧論文の紙コピーが 40 年分ある。
スキャナで PDF 化を進めているが、出来上がるのは「ファイル名だけのスキャン PDF」の山で、テキスト層が無いので一切検索できない。
学生に「Powers のあの議論を読んでおきなさい」と言っても、当の本人が現物のありかを探すのに午後が潰れる。

スキャンした PDF を LumenCite に追加していく。
DOI が判明するものは CrossRef、単行本は ISBN で書誌を解決し、古い紀要だけ手入力する。
別刷りと正誤表は同じエントリに複数 PDF として添付する。
スキャンにはテキスト層が無いので「未索引」のバッジが出る。
チャットに「この添付を OCR して索引して」と頼むと、Vision ベースの OCR が走って全文索引に入る。
索引済み添付への OCR は**ページを指定しても**拒否されるガードがあるので、二重に課金する事故は起きにくい。
別刷り（本体）が索引済みでも、テキスト層の無いスキャンは添付を名指しすれば OCR できる ──
拒否文が同じエントリの未索引 PDF を id つきで挙げるので、チャットはそちらへ切り替えられる。
数十冊を処理した週末、「type III 因子環の分類で $\lambda$ の値ごとに例を構成していた論文はどれか」と聞くと、全文検索が 1975 年のスキャンからスニペットつきでヒットを返し、該当節を読ませて要点を確かめた。

一方、元学生たちの近年の arXiv 論文には LCIR がそのまま効く。
ゼミ前には該当エントリにスコープを絞ったチャットで、`get_document_structure` に節構成と abstract を、`get_figures` に図の caption と生成 alt text を出させ、「Fig. 2 の相図が何を主張しているか」を PDF を開かずに把握してコメントを準備する。

40 年分の紙の蓄積が「訊けば出典とページごと返ってくる」ライブラリになり、学生への文献案内が「それは Powers 1975 の §3」という即答に変わる。

スキャン文献に効くのは OCR から全文検索までで、テキスト面の構造化は及ばない。
OCR テキストは LCIR に統合されていないため、スキャン PDF には定理ノードも参照グラフも記号定義も付かず、ページ単位の検索と読み出しが上限になる。
一方、ページ全体が画像であるスキャン本は図領域としては大量に拾われる（実測ではスキャン本 1 冊がライブラリ全体の figure ノードの 4 割強と crop 容量の 8 割を占め、自動 build と Vision 課金の最長ケースにもなる）。

## 五つのストーリーに共通する変化

ペルソナごとに使う機能は違うが、変化は 4 つに集約できる。

- **探す単位**：ページ送りと目視の探索が、定理、記号、図、式番号という論文の構成要素単位の問い合わせになる。
  単一文献の中でもライブラリ横断でも同じ粒度で引ける。
- **確かめるコスト**：LLM の答えにページ、領域、origin、confidence が付き、「答えが原文に基づくか」を答えごとに判定できる。
  チャットなら該当領域へ 1 クリックで戻れる。
- **転記**：TeX 版のある文献では数式が原文の LaTeX のまま取り出せる。
  citation key は決定的なので、refs.bib を何度再生成しても原稿の `\cite` は壊れない。
- **蓄積の性質**：構造化が取り込み時に自動で走るため、読んだ論文も積んだままの論文も同じ形で溜まり、数年後でも構成要素単位で再発見できる。

この 4 つが同時に成り立つのは、LCIR が最初から「原資料、位置、構造、由来、信頼度を失わずに保存する」ことを最優先に設計されているからである。
意味理解（要約や embedding）を先に狙う設計では、原文をモデルの表現へ変換した時点でページ座標と出典が落ちるため、答えの根拠を原文まで遡る機能は後付けできなかっただろう。

## v1.0.0 の LCIR がしないこと

ストーリーを誇大にしないため、v1.0.0 に入らないものを列挙する。
いずれも `docs/LCIR_REMAINING_PHASES.md` に post-1.0 として理由つきで記録されている。

- **数式の意味表現**：AST、Content MathML、OpenMath は持たない。
  TeX 版は生 LaTeX 文字列、PDF 版は表層文字列が上限で、意味的に同じ式の検索や式の同値判定はできない（Phase 7）。
- **PDF だけの文献の表と記号**：表のセル構造化と記号定義の抽出は TeX ソースがある文献に限られる（8d-6、debt-5）。
- **スキャン PDF の構造化**：OCR テキストは全文検索には入るが LCIR には統合されず、定理ノードも参照グラフも付かない。
- **embedding とベクトル検索**：横断検索は語彙の一致に限られ、言い換えや概念での検索はできない（10c）。
- **図の完全な回収**：caption を持たないベクター図は取り逃す設計で、寸法フィルタの都合で図が 0 件になる版も既知のまま残る（debt-26）。
  回転ページの図領域抽出も skip する（debt-9）。
- **図の中身の構造化**：図の種別分類（plot、diagram、photo）や、plot の軸と系列、diagram のノードとエッジは抽出しない（8d-4、8d-5）。
  SVG 形式の取り込みもしない（8d-3）。
  図の説明は caption と opt-in の Vision alt text（自然文のヒント）が上限になる。
- **標準形式エクスポート**：JATS、TEI、HTML+MathML、Web Annotation は出せない（9b）。
  出せるのは LCIR JSON と構造付き Markdown で、形式ごとに落ちる情報は欠落警告として明示される。
- **抽出器改良の自動反映**：既存文献の再構築は明示ボタンに限られる（脚注 [^rebuild] の理由による）。
